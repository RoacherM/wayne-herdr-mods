手机 App 与主动推送：设计原型

2026-11-06 · wayne-herdr-mods 0.1.7 · 状态：设计，未写代码 · 对应 Issue I-004

结论

  1. 收不到推送，先不用 App 也能解决。推送代码早就写好了。但你一直在 Chrome 标签页里用：最近 7 天 1790 条手机记录全是 browser: chrome、standalone: false，所以设备显示「推送关」。iOS 只给「主屏幕 Web App」推送。第 0 步：添加到主屏幕 → 重新扫码 → 打开推送。约 10 分钟，0 元。
  2. 独立 App 要付费账号才值得做。Apple 免费账号不能推送，装上的 App 7 天就失效。没有推送的 App 解决不了痛点 1。原生 App 需要 Apple Developer Program（$99/年）。
  3. App 是「薄壳」，不重写界面。你说现在的交互「非常 OK」，所以 App 里跑的就是现在的手机页（WKWebView，和 Safari 同一个 WebKit）。原生代码只做网页做不到的：锁屏通知上直接点「允许」、Face ID、钥匙串、扫码。估计 4–5 天（猜测）。
  4. 路线：先做第 0 步并用一周，量推送到达率。到达率够、且「点通知再回答」够用，就不花 $99；否则开账号做第 1–3 步。

1. 术语

术语意思
手机页 / PWA现在的手机网页（app/，托管在中继上）。PWA 是「可以装到主屏幕的网页」。
主屏幕 Web App从分享菜单「添加到主屏幕」后，从主屏幕图标打开的手机页。没有浏览器地址栏，有自己的存储，iOS 只给它推送。
Web Push浏览器标准推送。宿主把加密内容发给 Apple 的 web.push.apple.com，Apple 转给手机。
APNsApple Push Notification service，原生 App 的推送通道。需要付费开发者账号的 .p8 密钥。
薄壳 App一个很小的 Swift App，界面是一个 WKWebView（系统网页视图），里面加载手机页；只有推送、通知按钮、钥匙串这些用 Swift 写。
NSENotification Service Extension，App 附带的一段小程序。通知显示前，iOS 先交给它处理；我们用它解密推送内容。
通知按钮锁屏通知长按或下拉后出现的按钮（如「1 允许」）。Web Push 在 iOS 上没有这个能力。
宿主Mac 上常驻的 wayne-herdr-mods serve（host/）。
中继Cloudflare Worker（relay/），只转发密文。
nshNative Shell，用 TSX 写原生界面的框架。ios/ 里有第 0 步原型。本设计不再用它重写界面（见第 4 节）。

2. 事实：已验证的和猜测的

已验证（2026-11-06）

  • Web Push 链路代码完整：手机页 push.subscribe 订阅、设置页「发一条测试」、relay/public/sw.js 的 push / notificationclick（点通知打开那个终端）、宿主 host/push.js 发送（只发到白名单里的推送服务，含 web.push.apple.com）。从没在真 iPhone 上验证过（DESIGN.md 标「未测」）。
  • 你的设备 bf94d1e6 iPhone：「推送关」。指标文件 2026-10-31 至 11-06：1790 条手机记录，全部 chrome、standalone: false。
  • Apple 免费账号（Personal Team）不支持 Push Notifications 能力，签的 App 7 天失效（Apple 论坛、Supported capabilities）。
  • iOS 16.4 起，主屏幕 Web App 能收 Web Push，从 Safari、Chrome、Edge 添加都行；浏览器标签页里不行。iOS 26 的「添加到主屏幕」默认「作为 Web App 打开」。iOS 的 Web Push 通知没有按钮（OneSignal 文档）。
  • 本机有 Apple Development 证书（team 649Y392UFJ），没有付费账号。
  • nsh 0.4.0（2026-11-04）加了 lifecycle()（App 在前台还是后台）；推送仍需要自己写 Swift 宿主。
  • Herdr Anywhere v0.1.4（2026-11-05）：iPhone 版只在模拟器跑过，没有系统通知。它的终端也是 WKWebView 里的 xterm.js。

猜测，要量

  • iOS 26 上 Web Push 的到达率和延迟（第 0 步量）。
  • NSE 里用 CryptoKit 解密、通知按钮按 agent 的选项动态生成，都没做过原型。
  • 工作量全是估计。

4. 为什么 App 是薄壳，不用 nsh 重写

薄壳（WKWebView + 现在的手机页）nsh 重写（ios/ 原型、Herdr Anywhere 的做法）
交互和现在完全一样：键盘栏、语音、滑动看历史、直连都是现成的列表、发送框要重写，打磨过的细节要重做一遍
更新手机页仍从中继加载：npm run relay:deploy 后 App 立刻是新的，不用重装每次改界面都要重新打包安装
依赖只有系统 WebKitnsh 3 周大、0.x 版本，已踩过 wss:// 坏掉的坑
原生代码约 400 行 Swift + NSE（猜测）Swift 宿主 + 整个 TSX 界面
原生手感一般（仍是网页滚动）更好

终端掉帧（I-004 原来的启动条件 1）没有出现，所以不需要原生终端。以后真的需要，再在壳里换掉终端那一页。

7. 分步计划

第 0 步：主屏幕 Web App 推送（0 元，今天能做）

你做（约 10 分钟）：

  1. 在 iPhone 上用 Safari 或 Chrome 打开 https://herdr-relay.sir-housir.workers.dev，分享 → 添加到主屏幕，保持「作为 Web App 打开」开着。
  2. 从主屏幕图标打开。它的存储和浏览器分开，所以要重新扫码：在 Mac 的 Herdr.app 点标签栏右上角的手机图标。
  3. 设置 → 通知 →「开启通知」→ 允许 →「发一条测试」。

我做（0.5 天）：量推送到达率。宿主日志记下每条推送的发出时间和编号；service worker 收到时记下编号和延迟，下次打开时随指标上报。wayne-herdr-mods metrics 报告里加一行「推送：发出 N，收到 M，延迟中位数」。

用一周后的判断：到达 ≥ 95%、延迟中位数 < 10 秒、你觉得「点通知再回答」够用 → 到此为止。否则 → 第 1 步。

第 1 步：薄壳 App 上手机（付费账号；估计 1–1.5 天）

  • 新目录 ios-shell/（xcodegen 生成工程）：一个 WKWebView 加载 https://herdr-relay.sir-housir.workers.dev。
  • 麦克风和相机权限文案（语音、扫码在 WKWebView 里用 getUserMedia，和现在一样）。
  • 回到前台时通知手机页立刻重连（原生知道 App 状态）。
  • 用 Xcode 装到你的 iPhone；以后可以走 TestFlight。
  • 验证：devicectl 截图 + 手机页现有指标（src 记成 shell，能和浏览器分开统计）。

第 2 步：APNs 推送（估计 1.5 天）

  • 推送密钥：Swift 在钥匙串里生成一对 X25519 密钥，私钥不离开手机；NSE 和 App 共享钥匙串分组。公钥交给手机页。
  • 注册：手机页经现有加密连接调用 push.subscribe {apns: {token, env, key}}。宿主存到这台设备的 push 上。
  • 发送：host/push.js 加 APNs 通道，只用 Node 自带的 http2 和 crypto：ES256 JWT（.p8 存 Mac 钥匙串，命令 wayne-herdr-mods push apns-key，和语音密钥一样）。
  • 内容加密：X25519 + HKDF-SHA256 + ChaCha20-Poly1305（Node 和 CryptoKit 都自带，不加依赖）。通知上明文只有「Herdr：有终端需要你」，mutable-content: 1 让 NSE 换成真内容；NSE 失败时只显示这句，不漏内容。
  • 字段对应：Web Push 的 tag → apns-collapse-id（同一个终端的新通知替换旧的）；终端地址 → thread-id（按终端分组）；等你确认 → interruption-level: time-sensitive。

第 3 步：锁屏直接回答（估计 1.5–2 天）

  • 按钮从哪来：宿主读屏幕上的选项，每个 agent 一个读取器，只读用真样本测过的布局（~/.config/wayne-herdr-mods/asks/ 里已存了 claude、epi、agy 的真问题屏幕）。读不出就只有「打开」，不猜。这也是修「授权太贴合 Claude Code」的地方。
  • 按钮怎么生效：先做「点按钮 → App 打开到那个终端并替你按下数字」（简单，约 1–2 秒）。量过嫌慢再做后台发送（App 不出来）。
  • Face ID：会改东西的按钮都设 authenticationRequired：锁着的手机必须先解锁才能批准命令。
  • 防止答错题：新 RPC term.answer {address, turn, statusMs, key}。宿主先核对：这个终端还卡在同一个问题上吗（statusMs 没变）？变了就拒绝，回「问题已经变了」。10 分钟前的旧通知不会把「1」按进新问题里。

以后可选

  • 灵动岛 / 锁屏实时活动：「3 个在跑，1 个等你」，用 APNs 更新。
  • Android：同样的薄壳思路（WebView + FCM），没有需求不做。

8. 协议与兼容（DESIGN.md 规则 2）

组合行为
旧手机页 + 新宿主旧页面只发 push.subscribe {subscription}（Web Push），照旧工作。term.answer 旧页面不调用。
新手机页（浏览器里）+ 旧宿主不在壳里时不发 apns，和现在一样。
新手机页（壳里）+ 旧宿主旧宿主拒绝 apns 字段 → 页面提示「Mac 端要更新才能推送到 App」。term.answer 不在旧白名单 → 按钮退回「打开」。

中继地址、herdr-relay/v1、localStorage['herdr-relay'] 都不改。壳里的手机页是新存储，要扫一次码（和第 0 步一样）。

term.answer 和 push.subscribe 的 apns 字段改了宿主 RPC 白名单和凭证，按 AGENTS.md 规则 6 交给另一个模型独立审查。

9. 风险

风险应对
iOS Web Push 不稳定（被系统延迟或丢弃）第 0 步先量；不够就 B（Bark）或 C
手机页在 WKWebView 里和在 Safari 里行为不同（键盘、麦克风权限）第 1 步第一天就在真机上跑 dev/term-smoke.mjs 覆盖的操作
NSE 内存很小（24 MB 上限，猜测值），解密超时载荷只放标题、选项、编号；只用 CryptoKit
旧通知被点，按进了新问题term.answer 核对 statusMs
手机丢了：别人能在锁屏上批准命令按钮要 Face ID；Mac 上 devices rm 立刻作废
付费账号到期App 停推送，浏览器和主屏幕 Web App 照常能用
